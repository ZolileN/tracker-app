# Budget Tracker

Personal budget app for South African bank statements. Upload PDF statements from any South
African bank (Absa, Capitec, FNB, Nedbank, Standard Bank, GoTyme (TymeBank), Discovery, Investec, African
Bank, Bidvest, Old Mutual, Bank Zero and others) or a CSV, OFX/QFX or QIF download, check they
reconcile, categorise spending, and budget per pay cycle. Single HTML file, no server, no build tools.

## Supported statements

| Source | How it is read | Checked against |
| --- | --- | --- |
| Capitec, Nedbank, FNB PDF | Bank-specific parsers (`parseCapitec`, `parseNedbank`, `parseFnb`) | Real statements |
| Absa PDF (transaction history), Discovery PDF | Generic column parser | Real statements |
| GoTyme (TymeBank) PDF | Generic column parser | Fixture built from a real statement layout |
| Any other bank's PDF | Generic column parser (`parseGeneric`) | Layout fixtures in `tools/test_layouts.js` |
| CSV (with or without a header row) | `parseCsvStatement` | Layout fixtures |
| OFX / QFX, QIF | `parseOfx`, `parseQif` | Layout fixtures |

The generic parser finds the table by its column headings (Date, Description, Debit, Credit,
Amount, Fee, Balance in any order and wording), reads dates in any common format (including
year-less `12 Mar` and `03 12`, resolved from the statement period) and amounts written as
`-R1 234.56`, `250.00-`, `1 234.56 Cr`, `(80.00)` or `1 234,56`. It then follows the running
balance to settle each row's sign and whether a fee column was charged or only accrued, and
flags rows that do not follow it. If a bank-specific parser fails to reconcile (for example
after a layout change), the generic parser is tried and the better result is used.
Bank confirmation letters, empty periods and pending transactions are recognised and explained.

## Files

| File | What it is |
| --- | --- |
| `index.html` | The complete app, ready to open. Generated by `build.sh`; do not edit by hand. |
| `head.html` | Page markup and CSS (light + dark themes). |
| `parser.js` | Statement parsing: PDF text lines, bank detection, Capitec / Nedbank / FNB parsers, the generic column parser, CSV, OFX, QIF, reconciliation. Also runs in Node. |
| `app.js` | App logic: storage, categorisation rules, periods, screens, charts, import/export. |
| `build.sh` | Concatenates the three parts into `index.html`. |
| `tools/test_parser.js` | Runs the parser on real PDFs / CSV / OFX / QIF files in Node and prints reconciliation. |
| `tools/test_layouts.js` | Synthetic layout tests (Standard Bank, GoTyme (TymeBank), Discovery, Investec, Cr/Dr and accrued-charge styles, CSV, OFX, QIF). No PDFs needed. |
| `tools/build_excel_pilot.py` | Generates the Excel pilot workbook (openpyxl). Expects a JSON of parsed, categorised transactions; see the top of the script. |

## Run it

Open `index.html` in a browser. Data is saved in the browser's localStorage
(`budget-tracker-v1`). When hosted as a Claude artifact, it uses the per-person private
store instead (`claude.use("db")`, path `data/users/<id>/`), plus `claude.use("downloads")`
for file saves. Outside Claude those calls are absent and the app falls back automatically.

The only external dependency is pdf.js 3.11.174, loaded from cdnjs on the first PDF import.

## Change it

1. Edit `head.html`, `parser.js` or `app.js`.
2. Run `./build.sh`.
3. Test: `node tools/test_layouts.js`, then on real files:
   `npm i pdfjs-dist@3.11.174 && node tools/test_parser.js your-statement.pdf`

## Where things are in app.js

- `DEF_CATS`, `DEF_RULES`, `BANKCAT`: default categories, keyword rules, bank-category mapping.
  Built-in rules always come from the code (saved settings keep only the person's own rules), so
  new built-in rules reach existing users.
- `store`: load/save (cloud or localStorage), debounced writes, one document per month.
- `categorise()`: fee flag -> user rules -> built-in rules -> bank category -> fallback.
- `periodKey()`, `summarise()`: pay-cycle periods and income/spending totals.
- `viewOverview`, `viewTransactions`, `viewBudget`, `viewImport`, `viewSettings`: the five screens.
- `chartCumulative`, `chartTrend`: hand-drawn SVG charts.

## Adding a bank

Most banks need nothing: add the bank to `SA_BANKS` in `parser.js` (legal name and domain
markers, so a payment that mentions the bank does not change detection) and the generic parser
reads its table. Run `node tools/test_parser.js` on a few real statements and check that they
reconcile. Add a fixture to `tools/test_layouts.js` for any new layout trait.

Only if the generic parser cannot read a layout, write `parseXxx(lines)` in `parser.js` returning
`{ bank, account, tx:[{d, desc, amt, bal, bankCat?, fee?}], opening, closing, warnings }`,
add its detection to `detectBank()` and a branch in `parseStatementLines()`. Check that
`recon.ok` is true on several real statements before relying on it.
